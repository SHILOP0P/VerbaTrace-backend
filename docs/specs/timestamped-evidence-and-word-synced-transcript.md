# Спецификация: доказательства с переходом к аудио и пословная синхронизация транскрипции

Статус: ready for implementation
Область: `VerbaTrace/Monolit` и согласованные изменения `VerbaTrace-frontend`
Тип изменения: расширение модели транскрипции, результата анализа и интерфейса звонка с обратной совместимостью API

## 1. Цель

Реализовать две связанные пользовательские функции:

1. Любая подтвержденная цитата в анализе открывает точный момент записи.
2. Во время воспроизведения записи в транскрипции подсвечивается текущее слово.

После реализации пользователь может:

- нажать на доказательство в критерии или другом блоке анализа;
- перейти к соответствующей реплике и слову в транскрипции;
- начать воспроизведение с начала цитаты;
- видеть синхронную пословную подсветку во время воспроизведения;
- отличить связанную с записью цитату от цитаты, для которой точное место не найдено.

Главный принцип: таймкод не определяется языковой моделью. Backend связывает точную
цитату модели с сохраненными словами транскрипции. Если надежное соответствие не
найдено, цитата остается текстом без ссылки на аудио.

## 2. Исходное состояние

Текущий backend уже хранит у сегмента:

- участника;
- начало и окончание в секундах;
- текст реплики.

AssemblyAI возвращает пословные данные, но текущий `transcriptResponse` читает только
`text`, `language_code` и `utterances`. В `normalizeTranscript` сохраняются времена
реплик, а сведения об отдельных словах отбрасываются.

Результат анализа хранится как `call_analyses.result_json`. Поля `quote` и
`evidence_quotes` являются строками. В них нет идентификатора сегмента, диапазона слов
или времени записи.

API уже поддерживает `Range` для media-файла, поэтому новый маршрут для перемотки не
требуется.

## 3. Границы изменения

### 3.1. Входит в работу

- получение таймкодов слов от AssemblyAI;
- хранение и возврат слов через API транскрипции;
- детерминированное сопоставление точных цитат с диапазоном слов;
- структурированные доказательства в результате анализа;
- переход из анализа к транскрипции и media player;
- подсветка текущего слова при воспроизведении;
- обратная совместимость со старыми транскрипциями и анализами;
- тесты backend, frontend и видимого пользовательского сценария.

### 3.2. Не входит в работу

- редактирование транскрипции и участников;
- повторный анализ после исправлений;
- нечеткий семантический поиск цитат;
- генерация субтитров SRT/VTT;
- потоковая транскрипция в реальном времени;
- изменение аудиоплеера или провайдера распознавания целиком;
- автоматическое обогащение старых звонков повторным запросом к AssemblyAI;
- использование предположительных таймкодов, созданных языковой моделью.

## 4. Термины

### 4.1. Слово транскрипции

Один элемент упорядоченного массива слов, полученного от провайдера:

```go
type TranscriptionWord struct {
    Text         string   `json:"text"`
    StartSeconds float64  `json:"start_seconds"`
    EndSeconds   float64  `json:"end_seconds"`
    Confidence   *float64 `json:"confidence,omitempty"`
    Speaker      string   `json:"speaker,omitempty"`
}
```

Позиция слова в массиве является `word_index`. Она не сохраняется внутри каждого
объекта, а определяется индексом массива `words`.

### 4.2. Доказательство

Структурированная цитата из транскрипции:

```go
type AnalysisEvidence struct {
    Quote          string   `json:"quote"`
    StartSeconds   *float64 `json:"start_seconds,omitempty"`
    EndSeconds     *float64 `json:"end_seconds,omitempty"`
    WordStartIndex *int     `json:"word_start_index,omitempty"`
    WordEndIndex   *int     `json:"word_end_index,omitempty"`
    Speaker        string   `json:"speaker,omitempty"`
    MatchStatus    string   `json:"match_status"`
}
```

`word_end_index` включителен. Допустимые значения `match_status`:

- `matched` — найдено одно надежное соответствие;
- `ambiguous` — одинаковая цитата встречается более одного раза, выбрать место без
  дополнительного контекста нельзя;
- `not_found` — последовательность слов не найдена;
- `legacy` — старый результат анализа не содержит структурированной связи.

Для статусов, отличных от `matched`, временные поля и индексы должны отсутствовать.

## 5. Целевая модель данных

### 5.1. `call_transcriptions`

Добавить nullable JSONB-колонку:

```sql
ALTER TABLE call_transcriptions
    ADD COLUMN words JSONB NULL;
```

Значение — упорядоченный JSON-массив `TranscriptionWord`.

Правила:

- `NULL` означает, что транскрипция создана до внедрения функции или провайдер не
  вернул пословные времена;
- `[]` означает, что провайдер явно вернул пустой набор;
- времена хранятся в секундах как неотрицательные числа;
- `start_seconds <= end_seconds`;
- порядок массива соответствует времени произнесения;
- следующий элемент не обязан начинаться строго после окончания предыдущего;
- исходные миллисекунды AssemblyAI преобразуются в секунды один раз на границе
  провайдера;
- слова не дублируются внутри `segments`; сегменты и слова являются двумя
  представлениями одной транскрипции.

Добавить forward/down migration. Миграция не переписывает существующие строки.

### 5.2. Модели backend

Расширить:

```go
type Transcription struct {
    // существующие поля
    Words []TranscriptionWord
}

type TranscriptionResult struct {
    // существующие поля
    Words []TranscriptionWord
}
```

Repository method `MarkTranscribed` должен принимать и сохранять слова. Все его
реализации, моки и тестовые double обновляются явно.

### 5.3. Сегменты и слова

Сегменты остаются совместимыми с текущим контрактом. Связь слова с сегментом
вычисляется по временному пересечению и, если доступно, по `speaker`.

Не добавлять позиционные индексы слов в сегмент на первом этапе: они являются
производными данными и могут быть рассчитаны без дополнительного состояния.

Для режима без диаризации наличие `words` не зависит от наличия `segments`.
Пословная подсветка должна работать по общему массиву слов даже при пустом массиве
сегментов.

## 6. Получение данных от AssemblyAI

### 6.1. Контракт ответа

Расширить внутренний ответ провайдера:

```go
type word struct {
    Text       string   `json:"text"`
    Start      float64  `json:"start"`
    End        float64  `json:"end"`
    Confidence *float64 `json:"confidence"`
    Speaker    string   `json:"speaker"`
}

type transcriptResponse struct {
    // существующие поля
    Words []word `json:"words"`
}
```

Если актуальный ответ провайдера возвращает `speaker` только во вложенных словах
`utterances`, адаптер может дополнить его по соответствующей реплике. Глобальный
порядок и времена слов остаются каноническими.

### 6.2. Нормализация

`normalizeTranscript`:

1. Проверяет конечность и неотрицательность времени.
2. Пропускает элементы с пустым `text` или некорректным диапазоном времени.
3. Преобразует миллисекунды в секунды.
4. Сохраняет порядок провайдера, если времена не убывают.
5. Возвращает ошибку провайдера, если непустой массив слов имеет нарушенный порядок,
   который нельзя безопасно использовать для синхронизации.
6. Не применяет очистку, меняющую количество или границы слов.

Текст слова должен оставаться в форме провайдера, включая пунктуацию, необходимую
для читаемого отображения. Для сопоставления используется отдельная нормализованная
копия, а не изменение сохраненного значения.

### 6.3. Деградация

Отсутствие `words` не делает транскрипцию неуспешной. В этом случае сохраняются
текущие `text` и `segments`, а frontend показывает транскрипцию без пословной
подсветки.

## 7. API транскрипции

`GET /api/v1/calls/{uuid}/transcription` получает дополнительное поле:

```json
{
  "segments": [],
  "words": [
    {
      "text": "Здравствуйте",
      "start_seconds": 1.04,
      "end_seconds": 1.62,
      "confidence": 0.98,
      "speaker": "Менеджер"
    }
  ]
}
```

Контракт:

- поле `words` всегда присутствует;
- для старых записей возвращается `[]`;
- порядок элементов является частью контракта;
- API не возвращает внутренний transcript ID провайдера;
- права доступа совпадают с текущим маршрутом транскрипции;
- размер ответа контролируется интеграционным тестом на длинной записи.

## 8. Связывание доказательств с записью

### 8.1. Источник цитат

Модель продолжает возвращать точные `quote` и `evidence_quotes`. Она не получает
задачу вычислять `start_seconds`, индексы или идентификаторы слов.

После получения и проверки JSON результата backend выполняет отдельный
детерминированный этап `enrichEvidence(resultJSON, transcription.Words)` до сохранения
готового анализа.

### 8.2. Нормализация для поиска

При сопоставлении разрешены только преобразования, не меняющие смысл:

- Unicode case folding;
- схлопывание последовательностей пробелов;
- унификация `ё` и `е` только для поиска;
- игнорирование различий в крайних знаках пунктуации;
- сравнение последовательности нормализованных слов.

Запрещены на первом этапе:

- редакционное расстояние;
- поиск по смыслу;
- перестановка слов;
- выбор ближайшей похожей реплики;
- использование только первого и последнего слова длинной цитаты.

### 8.3. Алгоритм

Для каждой непустой цитаты:

1. Разбить цитату на нормализованные токены.
2. Найти все точные непрерывные диапазоны в нормализованном массиве слов.
3. Если найден ровно один диапазон — выставить `matched` и взять границы времени,
   индексы и участника из сохраненных слов.
4. Если найдено несколько диапазонов — выставить `ambiguous` без таймкода.
5. Если диапазон не найден — выставить `not_found` без таймкода.

Если цитата содержит слова разных участников, поле `speaker` не заполняется.

Нельзя молча выбирать первое совпадение: это может привести пользователя к неверному
моменту и создать ложное впечатление доказанности вывода.

### 8.4. Структура результата анализа

Добавить структурированное поле `evidence` рядом с каждым существующим полем цитат.
Пример критерия:

```json
{
  "code": "next_step_quality",
  "quote": "Давайте созвонимся во вторник",
  "evidence_quotes": ["Давайте созвонимся во вторник"],
  "evidence": [
    {
      "quote": "Давайте созвонимся во вторник",
      "start_seconds": 125.4,
      "end_seconds": 128.1,
      "word_start_index": 247,
      "word_end_index": 251,
      "speaker": "Менеджер",
      "match_status": "matched"
    }
  ]
}
```

Такое же обогащение применяется к поддерживаемым блокам результата, где уже есть
`quote` или `evidence_quotes`. Список JSON paths должен быть централизован и покрыт
тестами, а не размножен по обработчикам.

### 8.5. Обратная совместимость анализа

- существующие `quote` и `evidence_quotes` не удаляются;
- frontend сначала использует `evidence`, затем показывает строковые цитаты как
  несвязанный legacy fallback;
- старые `result_json` не мигрируются автоматически;
- повторный анализ нового звонка создает структурированные доказательства;
- API не подставляет вымышленные таймкоды в старый анализ;
- экспорт отчетов продолжает отображать текст цитаты, а при наличии связи может
  дополнительно показывать время в формате `мм:сс`.

## 9. Frontend: переход к доказательству

### 9.1. Поведение

Для `match_status=matched` цитата отображается как интерактивный элемент с временем.
При активации:

1. Открывается или становится видимой транскрипция звонка.
2. Плеер устанавливает `currentTime = start_seconds`.
3. Диапазон слов доказательства прокручивается в видимую область.
4. Диапазон получает отдельную подсветку доказательства.
5. Воспроизведение начинается только если это соответствует текущему UX кнопки;
   обычный переход не должен обходить browser autoplay policy.

Для `ambiguous`, `not_found` и `legacy` цитата остается обычным текстом без ложной
кнопки перехода. Допускается нейтральная подпись «Точное место не определено».

### 9.2. Координация компонентов

Не передавать команды плееру через глобальные DOM-события. Использовать единый
контроллер состояния страницы звонка или типизированный callback:

```ts
type MediaSeekTarget = {
  startSeconds: number;
  endSeconds?: number;
  wordStartIndex?: number;
  wordEndIndex?: number;
};
```

Плеер является источником текущего `currentTime`. Транскрипция получает его как
состояние, но не управляет воспроизведением напрямую, кроме явного пользовательского
действия перехода.

## 10. Frontend: пословная подсветка

### 10.1. Выбор активного слова

Активно слово `i`, для которого:

```text
words[i].start_seconds <= currentTime < words[i].end_seconds
```

В паузе между словами допускается сохранять подсветку последнего произнесенного слова
не более чем до начала следующего слова. После seek активное слово пересчитывается
сразу.

Поиск активного индекса выполняется бинарным поиском. Линейный проход по всему массиву
на каждом обновлении запрещен.

### 10.2. Частота обновления

- `timeupdate` используется как базовый источник позиции и fallback;
- во время воспроизведения плавное обновление выполняется через
  `requestAnimationFrame` с чтением `media.currentTime`;
- цикл останавливается на `pause`, `ended`, unmount и при невидимой вкладке;
- React state обновляется только при изменении активного индекса, а не на каждом кадре.

### 10.3. Отображение текста

Текст строится из сохраненных слов с корректным правилом пробелов перед знаками
пунктуации. Нельзя использовать `array.join(" ")`, если это создает пробелы перед
запятыми и точками.

Если `words=[]`, сохраняется текущее отображение `segments[].text` или общего `text`.

Должны визуально различаться:

- текущее слово воспроизведения;
- весь диапазон выбранного доказательства;
- текущее слово внутри выбранного доказательства;
- hover/focus интерактивной цитаты.

Подсветка не должна изменять размеры строк и вызывать скачки верстки.

### 10.4. Автопрокрутка

- при переходе по цитате прокрутка выполняется всегда;
- при обычном воспроизведении автопрокрутка следует за активным словом;
- если пользователь вручную прокрутил транскрипцию, автоматическое слежение временно
  приостанавливается;
- интерфейс показывает компактное действие «Вернуться к текущему моменту»;
- автопрокрутка не должна прокручивать всю страницу, только контейнер транскрипции.

### 10.5. Доступность

- цитата доступна с клавиатуры и имеет понятное accessible name с временем;
- цвет не является единственным признаком активного слова;
- контраст соответствует существующему UI;
- при `prefers-reduced-motion` используется мгновенная прокрутка без анимации;
- обновление каждого слова не объявляется screen reader через live region.

## 11. Ошибки и крайние случаи

Обязательная обработка:

- старая транскрипция без слов;
- старый анализ без `evidence`;
- слова есть, сегментов нет;
- сегменты есть, слов нет;
- одинаковая цитата встречается несколько раз;
- цитата модели отличается пунктуацией или регистром;
- цитата не является точной частью транскрипции;
- слово с нулевой длительностью;
- overlapping timestamps;
- seek за пределы длительности media;
- видео вместо аудио;
- временно недоступный media-файл;
- смена скорости воспроизведения;
- быстрые последовательные seek;
- длинная транскрипция с десятками тысяч слов;
- мобильный контейнер транскрипции;
- JSON старой версии, где `evidence_quotes` имеет неожиданный, но допустимый legacy
  формат.

Некорректный отдельный word-element можно пропустить с диагностикой. Нарушенный
порядок всего непустого массива нельзя незаметно сортировать, потому что индексы
являются частью сохраненного контракта.

## 12. Наблюдаемость

Добавить структурированные метрики или логи без текста пользовательских цитат:

- количество полученных слов на транскрипцию;
- доля готовых транскрипций с word timestamps;
- количество `matched`, `ambiguous`, `not_found` доказательств;
- длительность этапа сопоставления;
- количество отброшенных некорректных word-elements;
- frontend error telemetry для невалидного seek target.

Нельзя писать в production-логи полный текст транскрипции, цитаты или массив слов.

## 13. Безопасность и приватность

- `words` имеет те же ACL, что и полная транскрипция;
- новый публичный маршрут не создается;
- structured evidence не расширяет видимость звонка;
- аналитика и экспорт обязаны повторно использовать существующую проверку доступа;
- слова и цитаты считаются пользовательскими данными и не попадают в telemetry;
- удаление звонка должно удалять слова вместе с записью транскрипции;
- сроки хранения слов совпадают со сроками хранения транскрипции.

## 14. Порядок реализации

### Этап 1. Backend: слова

1. Добавить migration `call_transcriptions.words`.
2. Добавить `TranscriptionWord` в доменную модель и DTO.
3. Расширить AssemblyAI response и нормализацию.
4. Расширить repository, converter, service и API.
5. Обновить моки, fixtures и README API contract.

### Этап 2. Backend: доказательства

1. Реализовать изолированный deterministic matcher.
2. Добавить structured evidence enrichment после валидации ответа модели.
3. Сохранить совместимость `quote`/`evidence_quotes`.
4. Обновить экспорт и тесты результата анализа.

### Этап 3. Frontend: синхронизация

1. Расширить типы API.
2. Создать общий media/transcript controller страницы звонка.
3. Отрисовать слова без изменения существующей визуальной структуры реплик.
4. Добавить расчет активного слова и управляемую автопрокрутку.

### Этап 4. Frontend: доказательства

1. Отобразить связанные и несвязанные доказательства различимо.
2. Реализовать seek, прокрутку и подсветку диапазона.
3. Проверить все блоки анализа, содержащие цитаты.
4. Выполнить browser QA на реальном сохраненном payload.

Этапы backend должны попасть в production раньше или одновременно с frontend.
Frontend обязан корректно работать со старым API payload без слов и evidence.

## 15. Тестирование

### 15.1. Backend unit tests

- декодирование AssemblyAI `words`;
- перевод миллисекунд в секунды;
- сохранение текста, confidence и speaker;
- пустой массив слов;
- некорректные времена и нарушенный порядок;
- round-trip JSONB через repository converter;
- exact quote match;
- различия регистра, пробелов, `е/ё` и крайней пунктуации;
- unique, ambiguous и not-found match;
- цитата из нескольких слов и участников;
- отсутствие слов не ломает анализ;
- legacy analysis payload остается читаемым.

### 15.2. Backend integration tests

- migration forward/down на тестовой БД;
- `MarkTranscribed` сохраняет слова;
- `GET transcription` возвращает слова в правильном порядке;
- готовый анализ сохраняет structured evidence;
- ACL транскрипции и анализа не меняется;
- старые строки с `words IS NULL` возвращают `words: []`.

### 15.3. Frontend tests

- бинарный поиск активного слова на границах;
- обновление состояния только при смене индекса;
- корректное отображение пунктуации;
- fallback без слов;
- fallback старого анализа;
- click/keyboard по evidence вызывает правильный seek target;
- ambiguous/not-found evidence не является ложной ссылкой;
- ручная прокрутка приостанавливает follow mode;
- cleanup `requestAnimationFrame` при pause/unmount.

### 15.4. Browser QA

Проверить на реальной сохраненной записи:

1. Открыть звонок и начать воспроизведение.
2. Убедиться, что подсветка совпадает с произносимыми словами в начале, середине и
   конце записи.
3. Изменить скорость на `0.75x`, `1x`, `1.5x`, `2x`.
4. Выполнить seek мышью и клавиатурой.
5. Нажать доказательство и подтвердить точный переход к цитате.
6. Проверить мобильную ширину и длинную транскрипцию.
7. Проверить старый звонок без word timestamps.
8. Сравнить фактический API payload, отображенный текст и слышимый момент записи.

Компиляция без этого сценария не подтверждает готовность функции.

## 16. Производительность

- массив слов загружается одним существующим запросом транскрипции;
- активное слово ищется за `O(log n)`;
- на каждом animation frame не создаются копии массива слов;
- длинная транскрипция не должна полностью перерисовываться при смене одного слова;
- при необходимости список реплик виртуализируется, но выбранное доказательство и
  активная реплика должны оставаться адресуемыми;
- тестовый бюджет: переключение активного слова не создает заметных зависаний на
  транскрипции из 50 000 слов на целевом desktop browser;
- размер JSON payload измеряется на длинном звонке и фиксируется в результатах QA.

Сжатие HTTP может уменьшить payload, но не заменяет проверку стоимости разбора JSON и
рендера на клиенте.

## 17. Совместимость и выпуск

Порядок развертывания:

1. Применить additive migration.
2. Выпустить backend, который пишет и читает `words`, но сохраняет старые поля.
3. Убедиться по telemetry, что реальные новые транскрипции получают слова.
4. Выпустить frontend с fallback.
5. Включить structured evidence UI после проверки реальных совпадений.

Feature flag допустим только для frontend-представления. Сохранение слов должно быть
детерминированной частью новой транскрипции и не зависеть от пользовательского флага.

Rollback frontend безопасен, потому что старые поля сохраняются. Rollback backend
должен игнорировать дополнительную nullable колонку. Down migration выполняется только
после подтверждения, что новый backend больше не пишет `words`, иначе данные будут
потеряны.

## 18. Definition of Done

Работа завершена, только если одновременно выполнено:

1. Новая транскрипция AssemblyAI сохраняет упорядоченные word timestamps.
2. API возвращает слова, а старые записи — совместимый пустой массив.
3. Backend не принимает таймкоды доказательств от языковой модели.
4. Уникальная точная цитата получает проверяемую structured evidence связь.
5. Неоднозначная или ненайденная цитата не становится кликабельной.
6. Нажатие на связанную цитату переводит media и транскрипцию к одному моменту.
7. Во время воспроизведения подсвечивается фактически текущее слово.
8. Ручная прокрутка не конфликтует с автослежением.
9. Старые звонки и анализы продолжают открываться без ошибок.
10. Полные backend и frontend проверки проходят.
11. Browser QA подтверждает совпадение API payload, текста, подсветки и звука.
12. В логах и telemetry нет текста слов и цитат.
13. README и API-примеры обновлены.
14. После реализации кода выполнен `graphify update .`.

## 19. Открытые продуктовые решения

До реализации frontend владелец продукта должен выбрать:

- обычный клик по доказательству только перематывает или также запускает
  воспроизведение;
- показывать ли confidence слова пользователю или оставить только для диагностики;
- должна ли подсветка следовать за воспроизведением по умолчанию на мобильном экране;
- показывать ли время цитаты рядом с ней постоянно или только при наведении/focus.

Эти решения не меняют backend-контракт и не должны блокировать этапы 1–2.
